## Implémentation
- `JournalConversation` : journal JSONL par exécution dans `journaux/<id_execution>/conversation.jsonl`.
  - En-tête `contexte` : id_execution, modèle, prompt, plafond, date (plan_tests §9 : conservation avec contexte pour l'audit et tests TA).
  - Événements bornés : `message_utilisateur`, `raisonnement_agent` (texte émis entre tool_calls, avec n° de tour), `outil_invoque` (outil, arguments décodés, tour), `outil_resultat` (statut, message), `reponse_finale`, `plafond_atteint`, `erreur_api`, `fin` (statut : succes / succes_plafond / echec_technique).
  - Chaque ligne horodatée, portant id_execution ; flush à chaque écriture.
  - Échec d'écriture silencieux : la journalisation ne peut jamais interrompre une acquisition.
- Intégration dans `boucle_conversation` : paramètre `journal` optionnel (créé automatiquement sinon, injectable en test) ; les événements structlog existants sont conservés à l'identique.
- Rejeu : `lire_journal(chemin)` (tolérant aux lignes corrompues) et `extraire_invocations(journal)` — séquence ordonnée (tour, outil, arguments décodés, statut), base des vérifications TA-01 (intégrité identifiants) et TA-02 (ordre des appels). Les propriétés TA elles-mêmes restent à implémenter (T7.3).

## Décisions
- Répertoire dédié `journaux/` distinct de `logs/` : les logs structlog tracent le fonctionnement du code ; le journal de conversation trace le dialogue agent (charge utile complète, arguments et résultats) pour l'audit et le rejeu.
- Arguments journalisés **décodés** (dict, pas la chaîne JSON du tool_call) pour rendre le rejeu direct.
- Événements hors liste bornée remappés en `fin` (défense en profondeur contre les fautes de frappe).
